# M2.5-D8-B3 — explicit generation switch and rollback

## Scope and legacy boundary

Baseline: `fe3d626cb998f1d279d1f2531cc6eabb584aae28` (qualified B2).
The internal adapter is `src/activation/generation_operation.*`. It is not
installed as a public header and is not connected to CLI dispatch.
GenerationManager, legacy switch_to, rollback selection policy, D4–D8, B1,
B2, generation publication/discard, transaction leases and GC are unchanged.

Legacy switch_to already refuses a projection binding or CurrentV1, and its
callers retain their historical behavior. CLI rollback currently selects the
greatest retained numeric ID below current and invokes legacy switch_to. B3
does not replace either path, enumerate candidates or define a new selection
policy. Its caller explicitly chooses the target. A switch may go to any existing
generation, including a lower/equal ID; a rollback must go below its ORIGINAL
base ID. Neither operation infers history from activation-ID ordering.

B3 requires a bound context and an explicit SelectedBase with CurrentV1.
Absent/historical bases are refused: bootstrap/adoption/migration belong to the
existing explicit initial-activation APIs. No generation is created or restored.
The adapter is an implementation of the already-operational use case, not an
implicit migration of GenerationManager users.

## API and identity

- `GenerationOperationInput`: supplied ActivationId, ProjectionBinding,
  SelectedBase, target generation ID, complete preverified base/target source
  inventories and predecessor witnesses. IDs/ownership are never discovered.
- `prepare_generation_operation(context, held_state, kind, input, expected_digest)`:
  verify authority before reading generation paths, validate kind/direction/ID,
  read the exact base and target documents using the existing bounded no-follow
  reader, construct the complete B1 input, detach through B1.1, validate D8.1 and
  revalidate B1.3. Read-only; no barriers, archive mutation or D4 publication.
- `PreparedGenerationOperation`: immutable kind, B1 request and independently
  derived `GenerationOperationReference`. All fields and nested inventories own
  detached values. Copy/move does not expose mutable input aliases.
- `GenerationOperationReference { kind, RequestArchiveReference request }`:
  caller-retained intent plus B2 PlanIdentity/exact-envelope SHA-256. Retain it
  independently BEFORE persistence, including when persistence reports uncertainty.
- `persist_generation_operation(context, held_state, archive, operation)`:
  unchanged B2 persistence and B1.3; returns B2 Published/AlreadyPublished.
- `recover_generation_operation(context, held_state, archive, independently_expected)`:
  reject unknown kind before I/O, use B2 recover/B1.3, validate B3 selected-base
  shape and original rollback direction, return immutable claims. No activation.
- `activate_generation_operation(context, held_state, archive, independently_expected)`:
  ALWAYS recover again through B2/B1.3, then directly delegate to
  activate_prepared_operational -> D8.2 -> D4 -> fresh D6 -> fresh D7.
  There is no activation overload using a cached B3 observation or an unarchived
  in-memory request. Missing/corrupt/stale archive data never falls back to legacy.

The B1.1 envelope is the sole durable request format. Kind remains independently
retained caller intent; it is not added to that envelope or to the D8 digest.
The same lower-target request can be labelled switch or rollback because both
have identical execution semantics and authorization. A label supplies no authority.
The caller must authorize and preserve the intended kind independently; B3 does
not reconstruct it by interpreting untrusted archive data. A rollback label on
a non-decreasing request is rejected, even if its B1/B2 representation is valid.

ActivationId, PlanIdentity, PlanDigest, envelope digest and both original documents
remain fixed across retries. Selected-target rollback retries compare direction
against the original base, never the now-current target. Exact-ID/digest retry
uses B1/D8 semantics; a different CurrentV1, even for the same generation ID as
the original base, is stale. No rebase, new nonce, target substitution or implicit
base refresh occurs during recovery/activation.

## Authority, lifetime and GC

Every API requires exclusive caller-held ProjectionState throughout the call,
after any TransactionLease and before StoreGc. No additional lock, manager or
TransactionPins construction/handoff occurs inside the adapter. It does not
acquire a lease by decoding claims. Equivalent-authority writers/mount changes
must remain excluded; checks do not replace that contract or solve arbitrary ABA.

Caller inventories must already be complete verified snapshots. Structural B1
validation and exact filesystem document comparisons do not certify source
existence, seals, witness ownership, source durability or reconciliation. D6/D7
perform their existing fresh authorization even after successful B2 recovery.
Rollback has no weaker authorization branch, shell action or inverse legacy call.

The B2 root must already be durable, private 0700/effective-owner, dedicated to the
configured binding, in trusted ancestry and disjoint from operational authorities.
No implicit mkdir/chmod/root ownership or binding initialization occurs here.
The caller independently retains the reference; archive candidates are not a
source of expected hashes, intent, ownership or execution authorization.

During held State, cooperating discard/GC cannot invalidate generation/source
observations. Existing generation membership roots retain source payloads; D4/D5
take their existing request references when a plan/preparation is published.
B2/B3 do NOT retain generation metadata or sources after State release. Across
intervals/restarts the caller must arrange existing generation retention/pins
and verified source lifetime, then reacquire State and revalidate. No fake boolean
or serialized 'lifetime token' is introduced. If lifetime was lost, recovery refuses
missing/stale generations instead of reconstructing them or upgrading the archive
to a GC root. There is no promise of unconditional recoverability across arbitrary
discard or external mutation.

Tests demonstrate both sides: discard can remove a target referenced only by B2;
B3 subsequently refuses it, preserving the record. After D4 publication and a
later switch, inactive generation discard rejects the existing D4/D5 reference.
Actual privileged payload GC/authorization remains separately qualified.

## Failure atomicity and durability

B3 adds no durable file, journal, terminal marker or recovery scanner. B2 retains
its pending -> immutable-final protocol and write/fsync/rename/directory barriers.
Archive success never means selection or reconciliation success. Recovery may
repair/promote the independently pinned B2 envelope before discovering that its
B3 shape is invalid; that does not publish D4 or change current. This side effect
is explicit rather than concealed behind an assertion of globally read-only error.

B1 preparation preserves its existing SchemaError/ExecutionError/read exceptions.
B2 failures retain RequestArchiveError and archive-local uncertainty; they do not
classify a previous activation attempt. D8 failures retain OperationalActivationError
stage, identity, underlying cause and BeforeSelection/SelectionUncertain/AfterSelection.
No catch block deletes records/plans/generations, retries with a different request,
or claims that failure before THIS D8 call proves no earlier selection occurred.

Faults before/during B2 persistence preserve original intent and never execute.
Faults in B2 recovery barriers prevent D8 entry. D4 publication, D6 current rename
and D7 barrier faults preserve B2/D4 residues and retry through the exact original
request. A cached successful recovery is deliberately insufficient: activate
always rereads/revalidates the archive and current state.

## Qualification and explicit limits

The new nonprivileged generation_operation_test covers switch/rollback positive
roundtrips and selected retries, original CRLF documents, alias detachment, invalid
kind/direction/ID/base/binding/ownership/witness/digest, missing/corrupt/substituted
documents, absent/corrupt/symlinked/hardlinked archive records, same-ID collisions,
competing bases, replay, independent references, source-claim refusal, real local
hard-linked symlink witnesses, direct D2 substituted-witness refusal and preservation
of unrelated physical projection entries during an empty B3 transition.

For BOTH kinds it injects before/after faults at seven B2 persist events (28 cases),
three final-record recovery barriers (12 cases), D4 publication before/after rename,
D6 current before/after rename and D7 selected barrier (10 cases). Fifty injected
fault cases retain identity/state and retry through unchanged primitives. These
are syscall fault simulations, not power-loss experiments. B2's existing SIGKILL
matrix remains a required full-suite regression, not a new hardware guarantee.

Two fresh exec processes activate different requests from the same original base:
State serialization permits exactly one winner; the loser remains archived and
stale, without D4 publication. Manager reentry under State is rejected by the
existing process-wide hierarchy, and lifetime-gap discard is tested explicitly.
No universal concurrent C++ mutation or hostile namespace race proof is claimed.

Positive B3 activation fixtures have empty payload projections. Fabricated-source
cases are negative authorization tests, not physical source verification. The
physical witness case uses real local D2 inodes: D2 refuses a same-text replacement,
while B3 preserves that unrelated inode under the existing D6/D7 scope. It does
not authorize or modify the unrelated entry and is not a fully authorized nonempty
B3 transition. Privileged scanner/source/owner/mount/migration,
physical power-loss and OOM stress are NOT EXECUTED. TMPFS qualifies ordering and
process behavior, not reboot retention; targeted Btrfs tests do not prove power-loss.
ASan/UBSan results are finite checks; disabled LeakSanitizer supplies no leak proof.

Clean Debug/Release full qualification uses the existing explicit-source driver,
extended with this document, the two new module files, test and test binary. Hashes,
commands, configuration, results and audit are recorded in new B3 evidence bundles.
Prior qualifications remain immutable. No B4/B5/B6, CLI integration, automatic
rollback target policy, scheduler, migration, new pin protocol or GC change is included.
